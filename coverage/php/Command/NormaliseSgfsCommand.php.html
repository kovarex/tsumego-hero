20//first_move_color and correct_moves worked out again by besogo's rules, in the coordinates of the rewritten SGF.
21//The rows are rewritten in place, every version and proposal, so the versions of a problem stay in one frame and the
22//history compares like with like: no row is added, and the status, author, dates and review of a row stay as they
23//are. Its preview is made again from the new text. What goes with the coordinates follows the turn:
24//- the comments of a problem, kept in the coordinates of its current version, move with that version's turn;

26//- transformation_from_source, from the source version to this one, takes in both turns (source^-1, then the old
27//  transformation, then this one), each when that row is rewritten, so the result doesn't depend on the order.
28//A rewrite leaves out what besogo merges anyway (a line transposing into another, the moves after a ko comes round)
29//and what the board editor doesn't write (AP, CA, game info, + of a status problem). A row is kept as it is and named
30//when besogo would not play its rewrite the same (every move, transposition and correct or wrong end), or when the count
31//of a property changes in a way a save isn't expected to change it (propertyChanges of scripts/sgfCorrectMoves.mjs:
32//a G written on every node, a stone, label or comment lost on a node that stays). What was on a node besogo merges
33//into a transposition goes with it (its move, status, markup, comment); the report counts the rows stored with such a
34//loss and what went. Setup is written as besogo shows it, a point listed twice once: the play check compares the
35//stones shown, and the report counts the rows whose setup is written so. A status besogo can't read (S[undefined] of
36//old saves, or one whose + an old save wrote as a space, "A 2KO ") is left out, as every save does now, and counted;
